# V0.3 — Continuous Research: design, implementation and verification

**Status:** Implemented in a *stacked PR* atop V0.2-B; not an unrestricted cloud deployment.  
**Scope:** fact-level source-text changes, scheduling, local inbox, digest, run history and regression.  
**Parent:** PR #9 (V0.2-B Real Research Workspace) → PR #8 (V0.2-A demo).  
**Not shipped:** email/RSS/webhook delivery, multi-user SaaS, browser session replay, semantic proof of feature launches, real-world monitoring precision measurement.

## 1. Product outcome

A local operator can save an approved public-site research project, run it again,
inspect every material **supported price fact** change side by side with the old
and new page snapshot, identify uncertain changes separately, and mark updates
as acknowledged or irrelevant. The run history always distinguishes unreachable
sources from "no meaningful change".

A schedule is **opt-in** and requires a separate local tick invocation. No
unattended background agent is created and no notifications leave the machine.

## 3. The model: confirmed changes versus review candidates

**Supported change** is strictly a literal fact of the retrieved page text:

- `CHANGED`: both old and new sources contain an anchored price value and
  price/currency/period/billing conditions differ after normalizing the parser
  output; all sources associated with the subject succeed in both runs.
- `ADDED`: a fully retrieved prior source lacked a supported price, and the
  latest fully retrieved source explicitly provides one.
- `REVIEW_REQUIRED`: a previously supported price is no longer present,
  conflicts with another price, or a feature **keyword** becomes present/absent.
  These are **not** confirmed real-world removals or feature launches.
- **No event:** data was unchanged, noise changed but the normalized price was
  stable, both versions lacked evidence, or a required source failed to fetch.
  Failed/partial states remain visible in source health.

A source being unavailable is **never** equivalent to a verified deleted fact.
A different competitor's price cannot create a conflict for this subject;
source pages are grouped by the explicit **same subject label** recorded in the
project's immutable source list. Distinct currencies/periods/billing conditions
are not converted silently. Current deterministic extractor is intentionally
limited to price syntax and keywords; it does not certify feature availability,
real-world pricing, independent truth or legal terms. A normalized source claim
means a source literal was present, not that a human confirmed it.

## 4. SQLite V2 migration and correctness contracts

`ResearchStore` automatically creates `research_schedules`,
`research_changes`, and `research_reconciliations` and sets
`PRAGMA user_version=2`; old V0.2-B runs/snapshots remain intact. Unknown
higher schema versions fail closed. Ownership checks continue to use project
owner, **not the task namespace as an authentication mechanism**.

For each comparison:

1. Pick prior terminal run within the same project in persisted run order.
2. Inspect source status for the **same subject's complete source set** in both
   old and new run. If any fetch is missing or failed, never emit a confirmed
   change event.
3. Reduce each subject/field to supported literal values or an explicit
   insufficient/conflicted/review state.
4. Within `BEGIN IMMEDIATE`, insert unique `(run,subject,field)` event(s) and
   the `research_reconciliations` marker together. On fault all insertions roll
   back. Reprocessing the same run is idempotent.
5. Store source snapshot IDs, URL, exact quote, offsets and SHA-256 for old
   and new values. Only authenticated local operator can retrieve these.
6. Keep read state (UNREAD/ACKNOWLEDGED/IGNORED) separate from fact confidence.

The migration is create-only; no historical events are silently fabricated.
An older run that completes *after* a later run is not automatically replayed
retroactively; explicit `POST /api/v1/runs/{id}/reconcile` allows a local owner
to reconcile a specific terminal run. Scheduled runs are serialized per project
through an SQLite transaction, but operator-initiated concurrent manual runs
remain a documented sequence-consistency limitation.

## 5. Scheduling semantics

- Disabled by default. Enabled **only via an authenticated local request**.
- Interval: 1 hour to 30 days; UI exposes 1 hour, 1 day and 7 days.
- Configured budgets: `1≤pages_limit≤5`, `1024≤bytes_limit≤5000000`.
- SQLite `BEGIN IMMEDIATE` checks due time, active runs and existing
  last scheduled run, inserts a new bounded run and advances next due time in
  one transaction. Multiple processes cannot create duplicate jobs for a due
  interval.
- Interrupted CREATED or expired RUNNING scheduled work is discoverable by
  future ticks and protected by the V0.2-B worker-token fencing. Repeated
  dispatch can be at least once; source/result commits are idempotent per run.
- Missed intervals are **skipped**; no unbounded backfill. Disable a schedule
  explicitly to stop future due-run creation.
- **Nothing runs simply because an interval is set.** The operator must
  configure an OS cron or systemd timer, or use **Check due schedules locally**
  in the UI.

Local command:

```bash
python -m research_workspace serve --allow-host example.com \
    --db ./outputs/research_workspace.sqlite3
# In a separate terminal, or from a carefully configured cron/systemd timer:
python -m research_workspace tick --allow-host example.com \
    --db ./outputs/research_workspace.sqlite3
```

Use the **same** audited host allowlist and SQLite path for `serve` and `tick`.
Only public approved domains and server-side policy are eligible. Real cloud
outbound policy tests and independent review remain mandatory before exposing
anything beyond loopback local operation.

## 6. Local API contracts (bearer token + loopback host + origin checks)

| Method | Route | Response |
|---|---|---|
| `GET` | `/api/v1/projects/{id}/schedule` | schedule config and next due time |
| `POST` | `/api/v1/projects/{id}/schedule` | enable/disable, period and budgets |
| `POST` | `/api/v1/monitor/tick` | due run IDs queued to local worker (not external notifications) |
| `GET` | `/api/v1/projects/{id}/history` | run status and failed/missing source health |
| `GET` | `/api/v1/projects/{id}/changes` | old/new fact and exact evidence citations |
| `POST` | `/api/v1/projects/{id}/changes/{event_id}/ack` | ACKNOWLEDGED, IGNORED or UNREAD |
| `GET` | `/api/v1/projects/{id}/digest` | unread confirmed changes, review candidates and failed sources |
| `GET` | `/api/v1/projects/{id}/digest.md` | local Markdown digest download |
| `POST` | `/api/v1/runs/{id}/reconcile` | idempotent manual reconciliation after failure |

No public sharing, unrestricted URL, email sending, RSS, SMTP, paid plans or
multi-user tenant delegation is enabled. Share links and external delivery
require separate permission, privacy, audit and network controls.

## 7. Independent test datasets and acceptance

- 20 **synthetic, labeled and reproducible** before/after page pairs:
  changed prices, currency/period/terms, noise-only versions, missing values,
  conflicts and source fetch failures. These do not measure real-world recall.
- Cross-subject regression: one competitor's price must not affect another's.
- Coverage guard: if one of a subject's multiple sources is unavailable, no
  confirmed change can be published.
- Crash replay and fault injection: rollback and retry cannot double-insert.
- Authorization: one local operator cannot see or configure another owner.
- Scheduling race: 2 SQLite connections cannot allocate duplicate due run.
- Reopening a previous run preserves original snapshot and evidence hash.
- Existing V0.2-B database migration and project deletion cascade.
- Real Chrome E2E tests the UI, evidence details, acknowledgment, schedule
  configuration, local digest download, and 390px mobile width.

Automated tests are engineering gates. The PRD's **important-change recall
≥95% and alert precision ≥90% on independently labeled real-world sources**
remain OPEN. The current fixture 20/20 result must never be advertised as a
real-world 100% monitoring accuracy. Human screen reader and 7-day pilot cohort
have also not been completed.

```bash
python -m pip install -e '.[test,browser]'
python -m pytest -q tests/test_research_workspace.py tests/test_continuous_research.py
node --check apps/evidence-demo/src/live.js
npm --prefix apps/evidence-demo test
# Real Chrome requires browser + driver and a network-permitted local host:

```

## 8. Self-review, security and pending release gates

- Auth is local bearer token and loopback Host/Origin enforcement, **not**
  hosted/multi-tenant role-based auth. No claim of production SSRF resistance.
- Domain allowlist and robots are re-applied in each run (including ticks),
  with fetch byte count and per-run page limits inherited from V0.2-B.
- No LLM is trusted to label its own results supported. Untrusted source text
  is rendered using DOM `textContent`/`createTextNode`, not `innerHTML`.
- Local change inbox includes full old/new evidence; exports and API are
  authenticated and **not accessible from a public static hosting domain**.
- Deleting a project removes schedules, events, reconciliation checkpoints,
  snapshots and source text in the same SQLite transaction.
- No external push notifications or automatic daemon installed. Future
  delivery requires consent, privacy controls, retries and outbox tracking.
- Real-world semantic feature detection remains a research/evaluation task;
  keyword-only status is ALWAYS `REVIEW_REQUIRED` if changed.
- Production egress isolation needs real proxy/firewall with DNS rebinding,
  IPv6, redirects, metadata IPs, WebSockets and browser subresources checked.
- Long-term schedule health, backpressure under hundreds of projects,
  rate-control across **multiple OS processes** and alert channel preferences
  need production-specific benchmark and load testing.

**Overall:** feature-complete as a local V0.3 stage; not production-safe
arbitrary URL SaaS or empirically validated semantic monitoring accuracy.
