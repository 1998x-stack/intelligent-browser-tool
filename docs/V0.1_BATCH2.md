# V0.1 Batch 2 — SQLite Frontier integration (experimental)

This PR is stacked on V0.1 PR #1. Merge PR #1 first, then rebase and merge this one.
The default CLI remains backward-compatible. Enable persistence explicitly:

```bash
python run.py -u https://example.com -i "research" --no-selenium \
  --durable-frontier --no-search-seeds --max-pages 20
```

## Resume semantics
- State is saved under `<output_dir>/state/frontier-<task_hash>.sqlite3`.
- Task identity hashes start URL and intent; the same pair resumes its earlier state.
- The original seed step is skipped when the stored frontier already has entries.
- Each item is leased with a random token; stale workers cannot finalize another lease.
- An expired lease becomes eligible for reprocessing after its lease duration.
- A failure is scheduled with bounded retry delay; the current run may stop if no
  immediately eligible work exists. Invoke the command later to resume.
- Stored `parent_url` and `context` survive restarts.
- SQLite is a local single-host choice, not distributed exactly-once scheduling.

## Scope and security limitations
- The Requests engine validates URL syntax, host allowlist, and resolved
  addresses before each explicit redirect hop; it does **not** pin the
  socket's destination IP, and thus must not be exposed to arbitrary untrusted
  URLs without enforceable outbound network restrictions.
- Selenium still lacks mandatory navigation, redirect, frame and resource
  interception; secure browser networking is a separate high-priority PR.
- A URL-only allowlist is insufficient for full prompt-injection prevention.
- The durable scheduler is opt-in while integration/regression coverage matures.
- Existing on-disk V0.1 Frontier databases are migrated in place to include
  parent URL, context JSON and lease token.
- Saved reports are currently per invocation; previously persisted page
  findings are not yet aggregated into a single resumed report.
