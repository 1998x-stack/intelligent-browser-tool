# Historical V0.1 design note (PR #2)

This document describes the original parallel design proposal. Some choices
have been superseded by PR #1 and the following incremental SQLite implementation.

**Do not follow the old `--resume`/checkpoint instructions on current main**;
the current CLI uses an opt-in `--durable-frontier` flag only in later feature
branches. The old per-run JSON checkpoint code was not merged, because it
conflicts with the SQLite lease model and could overwrite the already-reviewed
URL policy. It can be reassessed as a separate migration proposal.

# V0.1 Foundation — implementation and acceptance

Status: offline regression tests passed (36/36 on Python 3.10 and 3.12); live browser and public-site acceptance pending.

## Scope

The existing flat Python modules are retained for backwards compatibility. V0.1
adds an installable CLI, central URL policy, browser redirect validation,
frontier acknowledgements and atomic task checkpoints. It intentionally does
not introduce Playwright, browser-agent actions, async concurrency or a WebUI.

## Run

```bash
python -m pip install -e ".[test]"
python -m pytest -q tests/
python main.py --url https://example.com/ --intent "documentation" --max-pages 5 --no-selenium
# Resume the same intent, URL and output directory:
python main.py --url https://example.com/ --intent "documentation" --max-pages 20 --no-selenium --resume
```

`--resume` requires `<output-dir>/state/run_checkpoint.json`; a missing,
corrupt or incompatible checkpoint is an error, not permission to silently
restart from scratch. Increase `max-pages` when continuing a task that has
already exhausted its prior budget.

## Architecture and invariants

- All URL admission paths must use `URLPolicy`. Hostname matching is
  exact or dot-suffix based; a host containing a trusted domain as a substring
  is not trusted.
- Private, loopback, link-local and other non-global IP addresses are rejected.
  The Requests engine resolves the hostname before each HTTP redirect hop,
  and does not use implicit environment proxies.
- Frontier `get_next()` leases a queued item; `mark_processed()` acknowledges
  its success/failure exactly once. A double acknowledgment raises an error.
- A frontier snapshot contains both queued and in-flight items; recovery
  returns in-flight items to the pending queue.
- A task checkpoint bundles frontier and prior PageResults into a single
  atomic file, avoiding cross-file recovery inconsistencies.
- Checkpoint restoration revalidates URLs and checks task identity before
  restoring progress. No automatic side effects are replayed.
- The crawler calls `close()` on every browser adapter type.

## Threat model and known limitations

This phase is a **preflight policy**, not a complete SSRF sandbox.

1. DNS rebinding can occur between the DNS check and the actual TCP connection.
   Production deployment still requires network egress restrictions or address
   pinning at the transport layer.
2. Selenium validates the final URL **after** browser navigation. An off-scope
   redirect may already have been contacted before rejection. Do not expose
   Selenium to untrusted external URL submissions without network isolation.
3. Robots.txt, crawl-delay, website terms, authenticated sessions, content
   sensitivity and per-origin rate budgets require additional policy work.
4. Frontier failure counts do not implement timed retry scheduling yet.
5. The legacy file-based data and report formats remain unchanged.
