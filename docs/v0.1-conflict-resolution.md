# PR #2 conflict resolution: preserve main URL boundary

This is a merge resolution between the parallel foundation implementation
(PR #2) and the already merged URL Policy + SQLite foundation (PR #1).

## What is retained

- `pyproject.toml` package metadata and installed `intelligent-browser` CLI;
  preserve the already-merged entrypoint from `crawler.py`.
- `main.py` compatibility entrypoint, previously an empty file.
- Remove the historical root `__init__.py`, which contained broken relative
  imports when pytest tried to collect the project as a package.
- Correct domain-boundary checks for extracted links in `content_extractor.py`.
- Python 3.10/3.12 package installation and CLI verification workflow.
- Historical design note, clearly labeled as superseded where it disagrees.

## Conflicting modules intentionally keep main's implementation

- `url_policy.py`: preserve `URLPolicy.validate()` API, exact domain matching
  by default, and public-address checks. Do not replace it with PR #2's
  `URLPolicy.check()` API, implicit subdomains or private-network opt-in.
- `browser_engine.py`: preserve the existing redirect and policy logic;
  PR #2's other method names are not compatible with PR #1 and subsequent
  `RequestsEngine` tests.
- `url_queue.py`, `crawler.py`: preserve already integrated queue lifecycle.
  The parallel `--resume` JSON checkpoint model is not silently combined
  with a transactional SQLite Frontier; that needs a separate, tested migration.

## Test rationale

PR #2's former checkpoint/URL tests assumed its incompatible `check()`
policy interface and private-network mode. The resolution replaces those
tests with focused merge regressions and keeps PR #1's foundation tests.
The historical designs are available in Git history.

## Validation and sequencing

1. Merge PR #2 to main only after its Python matrix and CLI workflow pass.
2. Bring PR #3's SQLite Frontier integration to main as a separately reviewed
   incremental PR, because the original PR #3 merged into a feature branch,
   not `main`.
3. Retarget PR #4 to the correct integration base or merge its prerequisites;
   retain PR #5 stacked on PR #4 until #4 is integrated.
