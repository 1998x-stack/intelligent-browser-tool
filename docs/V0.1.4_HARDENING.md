# V0.1.4 Production Hardening & Performance Evaluation

**Status:** implementation and CI evaluation. Production egress isolation is
**not certified** by tests that use an HTTP proxy alone.

## Logical task isolation
`--durable-frontier --task-namespace <namespace> --task-id <id>` partitions
SQLite databases by hashed namespace/task IDs, with a stored identity that
includes URL, intent, allowed hosts, and depth policy. Reuse of the same
namespace+ID with different identity fails closed. This is a **logical**
partition only, not process-level authorization, encryption, or filesystem
isolation. For a multi-user service, enforce separate OS identities or protected
directories, service-side tenant authorization and audit logs.

The default path changes to `<output>/state/<namespace-hash>/frontier-<task-hash>.sqlite3`
so old SQLite states from V0.1.3 are NOT silently adopted. Legacy data must be
audited and explicitly migrated separately. Keep old backups before upgrading.

## Retention and scheduler
- `FrontierState.enqueue_many` validates ALL entries before opening a single
  transaction, performing all-or-nothing batch admission.
- `DurableURLQueue.add_batch` applies existing normalization/filters.
- `FrontierState.prune_terminal(older_than_seconds=N)` explicitly deletes
  only terminal rows with a known finish timestamp, and their page results.
- Leased and queued jobs are not removed by retention. There is no implicit
  deletion or background maintenance.

## Reproducible performance tests

```bash
python -m benchmarks.frontier_scale --sizes 50 500 2000 --repeat 5 --output scale.json
```

The benchmark records median/p95/min/max elapsed time for both queues and
batched-vs-individual SQLite admission. No claim of superiority is made on
synthetic traffic; real web fetch and LLM time dominate typical workloads.

## Browser E2E and isolation boundary

The real Chrome/Selenium test drives the browser through a local controlled
HTTP proxy and checks navigation and subresource-blocking behavior. It verifies
the proxy path and rejects disallowed resources, but on a GitHub-hosted runner,
**it does not prove no direct socket egress is possible**. A separate
network-namespace or container-isolated browser + enforcement-proxy test is
required before claiming SSRF-safe deployment. Do not enable multi-tenant
browser use solely based on a passing CI proxy test.

## Follow-up production gates
- Validate real proxy/dns and direct-egress restrictions with a browser worker
  attached to ONLY an internal network, including redirects, subresources,
  WebSockets and alternate host protocols.
- Review the Squid ACL and Docker compose templates against a complete deny
  matrix (loopback/link-local/metadata/IPv4/IPv6, DNS rebinding, bypass routes).
- Add crash fault injection between HTML write, DB commit and report publish.
- Test concurrent workers under lease expiry and policy changes.

## Docker internal-network Chrome E2E

The separate `isolated-container-e2e` job runs a pinned Selenium
Standalone Chrome image on a Docker `--internal` network, with exactly one
local deny-by-default fixture proxy on that same network. The test checks:

- Real browser redirect to an allowlisted fixture through the proxy.
- Blocked cross-domain image/frame/fetch resources observed by the proxy.
- Separate browser session without the proxy cannot retrieve `example.com`
  on the internal-only network.
- Docker network inspection reports `Internal=true`, with precisely the
  two expected containers and no external bridge attachment.

This is an independent **container topology and navigation smoke test**,
not a comprehensive security assessment of Docker daemon/host routing,
IPv6, DNS rebinding, proxy ACLs, WebSockets or Chromium privilege boundaries.
The production Squid compose file is still not verified by this test.

### CI topology correction

The first Docker E2E attempt could not reach a published WebDriver port from
the host across the internal network. V0.1.4 now builds the test controller
image **before** creating the internal network, then runs Chrome, proxy and
test controller inside the same internal-only Docker network, with no
published ports. Selenium uses the internal DNS alias `isolated-browser`;
the proxy uses `local-proxy`. The test controller is removed before the
final two-container network inspection.
