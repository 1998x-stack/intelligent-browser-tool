# V04-01 — Identity / Workspace / Membership schema and safe SQLite migration

**Status:** Implementation and automated tests provided; stacked on V04-00 integration PR, **not** yet merged into `main`.  
**Scope:** internal data model, immutable membership audit, version-3 migration, WAL-consistent backup, legacy local-operator compatibility, and restricted internal membership operations.  
**Does not deliver:** login, email verification, SSO/OAuth, session cookies, public user APIs, invitation links, externally authenticated team permissions, hosted tenancy, remote MCP, or public arbitrary-URL execution.

## 1. Why data first

V0.3's `owner` column is a **server-configured local operator alias**, not a verified user identity. A public HTTP client must **not** be allowed to claim an alias and gain data access. V04-01 preserves this local access policy while preparing a genuinely explicit workspace boundary for V04-02.

This change is additive to the existing `research_workspace` module and does **not** modify public API routes. The local research service still checks its existing bearer token, loopback Host/Origin and owner alias exactly as before. No member management is exposed over HTTP.

## 2. Schema v3 and relationships

```text
users
  ├── workspaces.created_by
  ├── workspace_memberships.user_id
  └── legacy_owner_bindings.user_id

workspaces
  ├── workspace_memberships.workspace_id
  ├── projects.workspace_id
  └── legacy_owner_bindings.workspace_id

projects
  ├── owner         [preserved for V0.3 local API compatibility]
  ├── workspace_id  [backfilled and mandatory on new INSERT/UPDATE]
  └── created_by    [backfilled and mandatory on new INSERT/UPDATE]

membership_audit [append-only role/state change evidence]
```

New tables:

| Table | Key | Contract |
|---|---|---|
| `users` | `id` | Internal IDs; kind = `legacy_placeholder` or `unverified`; neither implies authentication |
| `workspaces` | `id` | Personal (migrated) or internal team workspace; creator FK |
| `workspace_memberships` | `(workspace_id,user_id)` | Role = owner/admin/editor/viewer; ACTIVE/SUSPENDED; unique per user/workspace |
| `legacy_owner_bindings` | `owner_alias` | One legacy alias -> exactly one local placeholder user and personal workspace; never a real login credential |
| `membership_audit` | `id` | Append-only, actor/subject, event, previous/current role, timestamp |

`projects` gains `workspace_id` and `created_by` fields. A SQLite trigger rejects new projects unless the creator is an ACTIVE member of that workspace. Another pair of triggers ensures that the last active Owner cannot be removed, demoted or suspended. Audit rows cannot be updated or deleted, including through ordinary direct SQL statements.

**Important:** V04-01's internal `WorkspaceRepository` accepts caller-supplied user IDs from trusted Python code. It enforces owner/admin restrictions as a *defense in depth*, not authentication. No external user input is accepted as a validated principal. V04-02 will introduce an authenticated `AccessContext` on each API call and replace all authorization based on the legacy `owner` alias. Teams in V04-01 are inert internal records until that occurs.

## 3. Migration semantics

1. When the DB is a nonempty legacy schema `0–2` with a `projects` table, `ResearchStore` first writes a new, local, **permission-0600 SQLite Backup API** copy beside the DB. This backup includes committed WAL pages and is validated with `PRAGMA quick_check`.
2. If backup fails, startup fails before any V3 schema change. The backup is never uploaded, overwritten or removed on success.
3. Existing v2 monitoring tables remain intact. `monitoring.ensure_schema` no longer downgrades a v3 database to user_version 2.
4. `migrate_v3` acquires `BEGIN IMMEDIATE`, creates identity schema and project fields, creates guards, and for every distinct persisted legacy `owner` deterministically creates a unique local placeholder user, personal workspace and active OWNER membership.
5. All historical project rows are backfilled with the matching `workspace_id` and `created_by`. Source pages, snapshots, fact claims, schedules, run leases, change events and run history are retained with their original IDs.
6. Only after successful backfill is `PRAGMA user_version=3` committed. An exception rolls back schema creation, altered columns, backfill and the version bump together.
7. Subsequent `ResearchStore` opens at version 3 do not create new backups or repeat project backfills. An unknown future schema version fails closed.

For truly historical owner strings (including blank or very long stored values), migration preserves the original alias instead of refusing an otherwise valid database; **new** local owner inputs are restricted to 1–200 nonblank characters.

### Compatibility

- The existing API and CLI continue working in **single-local-operator mode**. Newly created projects are automatically assigned the corresponding local personal workspace in the same SQL transaction.
- The old `owner` column remains so that V0.3 paths and tests continue to work; it is not a tenancy/security substitute.
- Upgrading is one way at the data level; there is no destructive down migration.
- Opening V0.3 pre-v3 databases with the new version automatically creates a pre-v3 backup. To avoid unexpected startup migration in production, stop the service and inspect the backup location before upgrading.

## 4. Safe deployment and rollback runbook

**Before upgrade:**

1. Stop the local `serve` process and any scheduled `tick`, and ensure no open writer continues while upgrading. Back up the database and any external file storage as per your normal operations policy.
2. Upgrade package, then start the local service. The first `ResearchStore` initialization creates the pre-v3 backup (for an existing v0–2 database) beside your configured DB: `research_workspace.sqlite3.pre-v3-<timestamp>-<nonce>.sqlite3`.
3. Verify the backup is owned by the operator and mode 0600, and verify schema version 3. Keep backups encrypted/permission-restricted if source text contains sensitive material.

**If migration fails:** automatic V3 migration runs in a single SQLite transaction and does not commit partial identity metadata. The original pre-v3 backup remains available for recovery.

**To roll back to V0.3:**

1. Stop **all** API and scheduler processes using the DB. Never restore while SQLite writers are live.
2. Keep a separate copy of the current v3 DB for incident review. Choose the correct, validated pre-v3 backup from this specific database and date.
3. Restore the backup to a **new** path using SQLite backup/copy while offline; do not leave stale `-wal` or `-shm` files from a different database at the restore target.
4. Verify `PRAGMA integrity_check`, expected project/run/snapshot counts and `PRAGMA user_version=2` (or the matching legacy version).
5. Use the matching **V0.3 code** with this legacy database. Running V04-01 code on the restored v2 database will upgrade it again automatically.
6. Never apply an old backup on top of new live writes without explicitly reconciling post-upgrade data loss.

### Read-only audit SQL

```sql
PRAGMA user_version;
PRAGMA integrity_check;
PRAGMA foreign_key_check;
SELECT count(*) FROM projects;
SELECT count(*) FROM snapshots;
SELECT count(*) FROM research_changes;
SELECT owner, workspace_id, created_by FROM projects ORDER BY owner;
SELECT workspace_id, role, state, count(*) FROM workspace_memberships GROUP BY 1,2,3;
```
